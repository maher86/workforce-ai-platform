# ADR 0005: Private normalized media and resumable report stages

Status: implemented for development; real-provider and pilot acceptance are separate gates.

SubmitReport accepts an actor, tenant, UUID submission key, text, MediaInput objects and optional work IDs. HTTP UploadedFile objects never enter the action. Active membership and same-tenant work associations are checked again inside a tenant-row transaction. Daily/storage limits are serialized there. A digest covers source text, original upload hashes and requested work associations; reusing a key with different content is rejected. Repeated identical requests return the original report.

Uploads are private. Content MIME, decoded dimensions, stream type and duration are checked; SVG/executables/video tracks are rejected. FFmpeg re-encodes images to bounded JPEG and audio to mono AAC/M4A, removes metadata and uses generated paths. Browser WebM can omit duration, so decoded output is measured and capped. Stored evidence is this normalized snapshot, not a byte-identical forensic original; the original source files are not retained separately. Unnecessary metadata and raw names are deliberately omitted. Normalized bytes have checksums. Report/tenant membership and media path ownership have database constraints. Download/stream endpoints authorize every request, including audio ranges, and use no-store/nosniff. No public storage link or service-worker cache is needed.

ReportSubmitted is dispatched after commit. A listener queues identifier-only ProcessReport jobs; dispatch outages leave persisted submitted rows for scheduler recovery. Each job performs one API stage within a 60-second timeout, saves it, releases its 90-second tenant/environment lock and dispatches the next job. Redis retry_after remains 180 seconds and each job has three attempts with bounded backoff. Completed stages are not repeated on ordinary retries/duplicate jobs. A provider success followed by a process/database failure before saving may still repeat a paid request; model cost limits and operator review remain necessary.

Stages: source-language transcript per audio -> English translation -> unverified image observations per image -> structured draft. Provider/model, prompt/schema version and usage accompany each immutable output. Responses requests use strict schemas and store=false. This is not a promise of zero provider retention; provider project data controls must be reviewed before real employee use. Quantity/completion claims require recognized evidence references and literal source quotes from text/audio. Image-only drafts use a server policy with no work claims. These checks cannot prove semantic factual accuracy. Human review, uncertainty and opt-in real-language evaluation remain release gates.

Employee content is only evidence in user input, never developer instructions or executable tools. No provider tools or remote attachment URLs are enabled. Job exceptions and database exception reporting redact payloads/bindings. Default demo mode explicitly performs no transcription, translation or image analysis; its UI and exports identify it. Production cannot resolve the demo provider.

Processing and review states are separate. Ready or failed reports can receive explicit human revisions with reason/version/actor, preserving generated outputs. Failed processing remains failed during manual approval. Retry clears review status to pending while retaining history and checkpoints. Only owners can irreversibly delete reports. Retention and orphan cleanup are scheduled and have dry-run commands; orphan cleanup ignores recent or referenced files.

Future WhatsApp adapters will resolve verified identity/tenant and supply MediaInput to the same action. They must not bypass MIME validation, quotas, idempotency, active membership or evidence rules.
